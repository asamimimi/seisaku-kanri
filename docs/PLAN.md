## 1. アプリの概要

フリーランスのWeb制作者が、1つの案件を次の3つの軸で管理するアプリ。

| 軸             | 内容                                                                                                   | 誰が動かすか       |
| -------------- | ------------------------------------------------------------------------------------------------------ | ------------------ |
| サイトマップ   | ページの親子関係（ツリー）                                                                             | 自分               |
| ① 制作フェーズ | ワイヤーフレーム作成 → デザイン → 実装中 → 実装完了 → 完了                                             | 自分               |
| ② 確認状況     | ワイヤー確認 / デザイン確認 / 最終確認（テスト環境）ごとに、未依頼・確認待ち・修正対応中・OK・確認不要 | クライアントの返事 |

**核になる機能「▲先行着手」**
クライアントのOK待ちのまま、ページが先のフェーズへ進んだ状態を、印を付けて見失わないようにする。

- 確認ポイントごとに「このフェーズに入る前にOKが必要」というゲートを決める
  - ワイヤー確認 → デザイン / デザイン確認 → 実装中 / 最終確認 → 完了
- 確認待ち・修正対応中のまま、ページがゲートのフェーズ以降にいれば先行着手
- 未依頼のまま進んだものは含めない
- 先行着手はDBに保存せず、ビューで毎回計算する（保存すると、OKが出ても印が残るなどの食い違いが起きるため）

**主な利用者**: 自分1人。v0.5でクライアントに閲覧用の共有リンクを出す。

## 3. 作業のルール

### コード
- CSSは `src/index.css` の変数（`--ink`、`--blue-bg` など）とクラスを使う。CSSライブラリは入れない。
- DBの読み書きは `src/lib/supabase.ts` の `supabase` を使う。画面用の集計はビュー（`project_overview` / `page_overview` / `page_confirmation_status`）から読む。
- 画面上の文言は日本語。コメントも日本語で、何のためのコードかを書く。
- ボタンや入力欄は高さ44px以上にし、キーボードでも操作できるようにする。
- 作業の区切りごとに `npm run build` と `npm run lint` を通す。

### DB
- 変更は `supabase/migrations/` に**新しいファイル**として追加する（既存のファイルは書き換えない）。
  - ファイル名: `YYYYMMDDHHMMSS_内容.sql`
- 新しいテーブルには必ずRLSを設定する（閲覧は全メンバー、編集は owner / editor）。
- 他の案件のデータを参照できないよう、外部キーは `(id, project_id)` の組で張る。

### セキュリティ
- `.env` はコミットしない。画面のコードに `service_role` キーを入れない。
- 画面に入れるキーは publishable（または anon）キーだけ。データはRLSで守る。

## 5. 補足: ページの親子が輪にならないようにする仕組み

`pages` は `parent_id`（親ページのID）でツリーを作っている。今のSQLで防げるのは、**自分自身を親にすること**だけ。

ドラッグで階層を変えると、次のような操作ができてしまう。

```
会社概要
 └ 代表挨拶
```

この状態で「会社概要」を「代表挨拶」の子に移すと、

```
会社概要 の親 = 代表挨拶
代表挨拶 の親 = 会社概要
```

となり、親をたどると永遠に戻ってくる。どちらも一番上（親なし）にならないので、サイトマップに表示されなくなる。表示の処理によっては、画面が固まることもある。

**対策**: ページの親を変えるとき、DBのトリガーで新しい親の先祖を上へたどり、途中に自分が出てきたら保存を拒否する。画面側でも、自分の子孫の中へはドロップできないようにする（DBの仕組みは、画面の不具合があっても守るための最後の防波堤）。

- DB側: `supabase/migrations/20261014000000_pages_prevent_cycle.sql`。拒否されると supabase-js では `error.code === '23514'` が返るので、画面で「移動できません」と表示する
- 画面側: ページ編集ダイアログの「親ページ」から、自分と子孫を外している（`src/lib/sitemap.ts` の `collectDescendantIds`）。ドラッグでも同じ関数でドロップ先を禁止している（`planMove` と、ドラッグ中の子孫の行の `useDroppable` を無効にする）

## 6. 決まっていること

| 項目                                  | 決定内容                                                                                     |
| ------------------------------------- | -------------------------------------------------------------------------------------------- |
| ログイン                              | Googleログインのみ                                                                           |
| 先行着手の対象                        | 確認待ち・修正対応中のまま、ゲートのフェーズ以降へ進んだもの。未依頼は含めない               |
| 進捗バーの区分                        | 設計（ワイヤーフレーム作成・デザイン）／ 実装（実装中・実装完了）／ 完了                     |
| 「納期が近い」の基準                  | 7日以内（`src/pages/Projects.tsx`）                                                          |
| サイトマップの確認状況の1行表示（案） | 確認待ち・修正対応中（先行着手なら▲を付ける）→「✓すべてOK」→ 一番後ろのOK → 未依頼、の優先順 |
| スケジュールの単位                    | ページごとに4つの期間（WF / デザイン / 実装 / 最終確認・調整）の開始日・期限。担当は持たない（利用者は自分1人） |
| 期間が「済み」になる条件              | 制作フェーズが WF→デザイン以降 / デザイン→実装中以降 / 実装→実装完了以降 / 最終確認・調整→完了 に進んだとき（`src/lib/schedule.ts`） |
| 期限切れ・期限が近い                  | 済んでいない期間で、期限を過ぎたものが期限切れ、期限まで3日以内（今日を含む）のものが期限が近い |
| 工程テンプレート                      | 作らない。フェーズの並びは全案件で固定 |
